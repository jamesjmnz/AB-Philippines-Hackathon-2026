# Contributing to PULSE 2.0

This policy is for **Claude Code, its delegated agents, and human contributors**. It is embedded in and generated by the authoritative PULSE master prompt. Follow existing repository protections and licensing requirements when they are stricter.

## Principles

- Preserve the user's existing application, Cal AI-inspired design implementation, and handwritten changes. Inspect before editing; build working behavior rather than replacing it with mock UI.
- Keep **Callstack React Native AI (`@react-native-ai/apple`) the primary Apple Intelligence integration**. Use small Swift native modules only when there is a proven gap (for example peer transport, CryptoKit/Keychain, or Core Motion).
- Manual SOS must work independently of AI; represent queued/delivered/acknowledged/accepted/completed/resolved distinctly. Never call simulated behavior verified hardware behavior.
- Keep privacy, explicit consent, trusted pairing and encrypted messages in scope; never include real sensitive incident data in source, logs, fixtures or demos.
- Source documentation goes into `docs/` (architecture decisions, phase progress, benchmarks, test evidence, threat model, limitations and demo runbook). Update docs in the same change as the feature they describe.

## Branching and ownership

- Preserve existing branch policies. Prefer `feat/<short-topic>`, `fix/<short-topic>`, `chore/<short-topic>` for work needing review; use the existing current branch where permitted.
- **Repository-specific rule:** `main` is not pushed to directly. Work lands on a feature branch (currently `feat/pulse-2`) and reaches `main` through a pull request that the repository owner merges.
- Subagents may edit only their owned paths and must report changed files/tests. **Only the lead Claude Code orchestrator stages, commits, pushes, merges and opens PRs.**
- Never perform force pushes, rebases of published branches, history resets, auto-merges through protection, hook bypasses or unrequested repository deletion.
- An authorized existing `origin` permits normal pushes to the current unprotected branch after reviewed, verified phase gates. If remote or authentication is missing, document the blocker and continue code work; ask before creating a new repository or deciding its visibility.

## Conventional Commits (semantic commits)

Format:

```text
<type>(<scope>): <imperative summary>
```

Recommended types: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`, `ci`, `chore`, `style`, `revert`.

Recommended scopes: `init`, `ios`, `ai`, `carechain`, `capsule`, `peer`, `crypto`, `db`, `ui`, `eas`, `docs`, `test`, `demo`.

Examples:

```text
chore(init): initialize Expo Router and NativeWind
build(eas): add iOS development profile
feat(ai): add Callstack local incident parsing
feat(carechain): track human-confirmed clarifications
fix(peer): preserve outbox when nearby device disconnects
test(crypto): reject tampered capsule payloads
docs(demo): document real three-device test limitations
```

Commit subjects should be concise, descriptive, and focused, ideally under 72 characters. One logical concern per commit. Explain complex changes in a human-readable body when useful, but do not fabricate passing tests or performance results. Mark breaking changes using `!` / `BREAKING CHANGE:` only when actually warranted.

### Keep commit messages free of unnecessary metadata

- Do not append `Co-Authored-By: Claude`, `Generated by Claude`, `Written with AI`, tool session identifiers, AI watermarks, marketing footers or irrelevant links.
- Do not append `Signed-off-by` trailers unless required by policy. Do not evade hooks or required legal attribution; flag the conflict.
- Respect the configured Git author/email and any required cryptographic signing. **Do not strip Git's inherent author, committer, date, object hash, or required provenance.**
- Keep copyright notices, open-source licenses, Callstack attribution where required, and truthful hackathon AI-tool/model disclosures.

## Commit and push checklist

1. Review `git status --short` and inspect the intended diff. Never include unrelated dirty files.
2. Confirm no credentials, production environment files, real location/medical data, certificate material, `.DS_Store`, private demo footage, EXIF GPS metadata in new distributable images, or large generated outputs are staged. Preserve source images and clean only derived assets deliberately.
3. Stage deliberate file paths, run `git diff --cached --check` and inspect `git diff --cached --stat`.
4. Run applicable tests, strict TypeScript checks, lint, Expo doctor and targeted native builds when possible; document blocked tests.
5. Commit using the Conventional Commit message format without unwanted trailers.
6. Push normally to the authorized remote after the verified milestone (respect protected branches and PR requirements). Never force push.
7. Record the phase, test evidence, commit hash, branch, GitHub push result and blockers in `docs/AGENTIC_PROGRESS.md`.

## Pull request / milestone review

A review description should summarize the problem and implementation, tests actually run, iPhone/iOS coverage, behavior still mocked, offline implications, privacy risks, screenshots only if they contain no sensitive content, and any human-only verification steps. Do not claim physical-device verification from simulator results.

## Definition of done

A phase is complete only when the implemented behavior meets its documented gate and the relevant checks have genuinely passed. Git commits or successful GitHub pushes **do not themselves prove** real Apple Foundation Models inference, Bluetooth/Wi-Fi peer delivery, encryption security or rescue outcomes.
