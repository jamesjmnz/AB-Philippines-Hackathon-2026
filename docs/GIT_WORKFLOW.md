# Git workflow

Short checklist version of [`CONTRIBUTING.md`](../CONTRIBUTING.md), which is the full policy. If the two differ, `CONTRIBUTING.md` wins.

## Repository

| Item | Value |
| --- | --- |
| Remote | `origin` = `github.com/jamesjmnz/AB-Philippines-Hackathon-2026` (public) |
| Default branch | `main` |
| Working branch | `feat/pulse-2` |

The repository is public. Treat everything committed as published.

## Branch and PR rule

- `main` is never pushed to directly.
- Work lands on a feature branch (`feat/<topic>`, `fix/<topic>`, `chore/<topic>`; currently `feat/pulse-2`).
- It reaches `main` through a pull request that the repository owner merges.
- A draft PR from `feat/pulse-2` to `main` will be opened in Phase 1. It has not been opened yet.

## Who runs Git

Only the lead orchestrator stages, commits, pushes, merges and opens PRs. Delegated agents edit their owned paths and report; they never run `git add`, `git commit`, `git push`, `git merge` or `gh pr`.

## Commit message format

```text
<type>(<scope>): <imperative summary>
```

- Types: `feat`, `fix`, `refactor`, `perf`, `test`, `docs`, `build`, `ci`, `chore`, `style`, `revert`.
- Scopes: `init`, `ios`, `ai`, `carechain`, `capsule`, `peer`, `crypto`, `db`, `ui`, `eas`, `docs`, `test`, `demo`.
- Subject under 72 characters where possible. One logical change per commit.
- **No AI trailers**: no `Co-Authored-By`, "Generated by", "Written with AI", session identifiers or tool footers. AI-tool use is disclosed in [HACKATHON_DISCLOSURES.md](HACKATHON_DISCLOSURES.md).
- No `Signed-off-by` unless a policy requires it.
- Do not alter author, committer, dates or signatures.
- Never state in a commit message that a test or device check succeeded unless it did.

## Checklist for every commit and push

1. `git status --short`. Leave unrelated changes alone.
2. Confirm nothing sensitive is included: credentials, `.env` files, `.p8` / `.p12` / provisioning files, device identifiers, real location or health data, `.DS_Store`, logs, demo recordings, large generated output.
3. Stage named paths: `git add <paths>`. Never `git add -A` or `git add .`.
4. `git diff --cached --stat` and `git diff --cached --check`. Read the staged diff.
5. Run what applies: `npm run typecheck`, `npm run lint`, `npm test`, `npm run doctor`, and a native build when the change touches native configuration. Write down anything that could not be run.
6. Commit with a Conventional Commit message.
7. `git push` (first time: `git push -u origin feat/pulse-2`).
8. Record phase, test evidence, commit hash, branch, push result and blockers in [AGENTIC_PROGRESS.md](AGENTIC_PROGRESS.md). Write `PUSHED` only after Git confirms.

## Never

- `git push --force` or `--force-with-lease`.
- Rebase, reset or amend commits that have been pushed.
- `--no-verify` or any other hook bypass.
- Change branch protection, remote URLs or author identity.
- Create a new repository or change visibility without being asked.
- Commit the generated `ios/` folder.

## If a push is not possible

Record `BLOCKED` with the exact reason in [AGENTIC_PROGRESS.md](AGENTIC_PROGRESS.md), keep committing locally, and continue work that does not depend on it. Do not claim a push that Git did not confirm.

## Pushed is not verified

A commit or a successful push proves nothing about on-device inference, peer delivery or encryption. Gates are passed only by the evidence defined in [PHASE_PLAN.md](PHASE_PLAN.md).

## Pull request description

Summarise: the problem and the change, tests actually run with results, iPhone and iOS coverage, what is still mocked, offline implications, privacy risks, and remaining human-only verification steps. Screenshots only if they contain no sensitive content. Do not claim device verification from anything other than a device.
