# Local AI benchmarks

**Measured numbers live in one place: [`ml/RESULTS.md`](../ml/RESULTS.md).** This document holds no results. It says how measurements are taken and what makes one count.

`ml/RESULTS.md` is generated by `npm run ml:report` from the result files committed under `ml/benchmarks/`. Anything not run is written there as unverified. The workspace, its datasets, the scorer and the metric definitions are described in [`ml/README.md`](../ml/README.md).

The single observations made by hand on a phone (the output-shape probe and a few extractions) are recorded in [LOCAL_AI.md](LOCAL_AI.md) under "Device observations". They are observations, not benchmarks.

## Rules

- Measured numbers only. No estimates, no vendor figures, no numbers from Demo Lab or from tests using a fake model. A simulated call reports no latency at all.
- A row is an on-device model result only if its result file says it ran on a physical iPhone and every model call in it came from the on-device provider. Baseline and simulated runs are reported in their own section, without latency.
- Each result file names the device, iOS version, package version, prompt version, app commit, split, variant, start time and the conditions typed in by the person running it (network state, phone language).
- Inputs are synthetic and written before any model or rule is run on them. Reference answers are frozen and never leave the Mac; the phone reads the statements only.
- External internet is disabled during measurement (airplane mode; Wi-Fi and Bluetooth radios re-enabled only if the scene needs peer transport).
- Report text is not logged. A result file holds outputs, typed states and timings, never the scenario text.
- English and Taglish are reported apart, with the sample size beside every rate.

## What is measured

Defined in `ml/evaluation/scoring.ts` and listed in `ml/README.md`: field correctness, unknown kept unknown, unsupported-fact rate, delta class accuracy, conflict precision and recall, clarification relevance, forbidden leaks, schema validation, evidence check, calls by typed state, and latency over completed model calls on the device with the first call reported apart.

Not measured by the evaluation runner: capability check time, embeddings, transcription, `prepare()` time and memory. None of these has been run on a device.

## Procedure

1. Install the development build on the device. Note the build and the app commit.
2. Confirm Apple Intelligence is enabled and the model is downloaded (text model only).
3. Enable airplane mode. Confirm no external connectivity.
4. Open `Settings > Demo Lab > Local AI`. Confirm the screen says the calls are real, not simulated, and that the text capability is ready.
5. Leave the app otherwise idle. The evaluation run calls the adapter directly, not through the app's model lane, so other model work at the same time would disturb the timings.
6. Under "Evaluation run" choose the split and the variant (`rules`, `staged`, `single`, `quotes`, `nested`), type the conditions, and run.
7. Share the exported JSON file off the phone and save it into `ml/benchmarks/device-results/`.
8. On the Mac: `npm run ml:verify`, `npm run ml:score -- <file>`, then `npm run ml:report` to regenerate `ml/RESULTS.md`.

The held-out split is looked at once per prompt version (`ml/README.md`, rule 4).
